# Workflow Contract Normalization Design

## Purpose

Convert the 2026-06-21 comprehensive workflow audit into one canonical repair program for Superpowers Project.

The goal is to make the project workflow more predictable, easier to maintain, and harder to drift by replacing repeated route and continuation policy copies with source-owned contracts, compact metadata, validator-backed generated surfaces, durable decision records, clearer review output, and focused workflow examples.

## Source Audit

- `.chatgpt/audits/2026-06-21-superpowers-project-comprehensive-workflow-audit-for-issues.md`

The audit is a handoff packet, not canonical project documentation. This spec promotes its findings into the durable Superpowers Project artifact model so downstream planning, issue creation, implementation, validation, merge closeout, and live sync can proceed from repo-owned source material.

- `docs/superpowers/PROJECT_CONTEXT.md` lists `M0 - Governance`, `M1 - Source Of Truth`, and `M2 - Distribution`; this work belongs primarily to M0 and M1.
- `README.md` and `docs/superpowers/OUTCOME_WORKFLOW.md` both describe native continuation geometry, workflow mode selection, route surfaces, proof gates, and artifact review rules.
- `docs/superpowers/OUTCOME_WORKFLOW.md` is generated by `scripts/generate-outcome-workflow-summary.ps1`, proving some route documentation is already generated and should be extended rather than duplicated by hand.
- `skills/write-plan/agents/openai.yaml` still says `project_plan_issue_execution_route` includes `Resolve Issue`, `Orchestrate Issues`, and `Stop`.
- `skills/write-plan/SKILL.md` defines `project_plan_issue_execution_route` as a nested Yes-route with `Resolve Issue` and `Orchestrate Issues` only.
- `skills/*/agents/openai.yaml` prompts remain large; the largest observed prompts range from 10,272 bytes to 6,282 bytes for most workflow skills.
- `scripts/test-native-continuation-loop.ps1` already validates repeated continuation phrases across skills; this confirms current validation depends on duplicated prose rather than a central policy reference.
- `.superpowers/**` is local generated run state and should stay non-canonical except when a workflow intentionally reviews a run ledger.

## User Decisions

- Use one umbrella spec instead of splitting the audit into separate specs before planning.
- Use Design 1: registry-first normalization.
- Include all ten audit slices as implementation tracks in this spec.
- Preserve strict native continuation, artifact review, stop/done, proof, merge, and live-sync gates.
- Prefer loud validation failures over permissive behavior when route surfaces drift.

## Design Alternatives Considered

### Design 1: Registry-First Normalization

Create one machine-readable workflow contract, validate or generate duplicated route surfaces from it, shrink metadata prompts to routing hints, centralize global continuation policy, then layer Decision Ledger, Artifact Review Card, backlog signal, examples, worker packets, and drift checks on top.

This is the selected design because the audit's concrete failure is contract sprawl causing drift. The `write-plan` metadata mismatch is a live example that one authoritative route source would catch.

### Design 2: Validator-First Hardening

Keep current prose mostly intact at first, add validators for route mismatches, metadata drift, decision ledgers, generated state, and examples, then compress prose and metadata later.

This lowers near-term behavior risk, but it validates a still-duplicated model. It would make the follow-up cleanup larger and keep agents reading repeated walls of policy until a later phase.

### Design 3: Authoring-Friction First

Start with templates, output cards, examples, issue packet samples, and backlog cleanup, then add the canonical registry after the workflow is easier to use.

This improves daily usability, but it does not fix the highest-risk route drift. It also risks creating templates and examples that need to be rewritten once the registry lands.

## Recommended Approach

Implement Design 1 as an M0/M1 repair program with independently verifiable tracks.

The registry is the core boundary: it must define active workflow skills, question IDs, prompt text, top-level options, nested route options, terminal rules, final health gates, validators, expected output artifacts, route ownership, and next-skill transitions. Every other route surface should either be generated from it or validated against it.

The first implementation plan should keep changes sliceable:

1. Create the canonical registry and registry validator.
2. Use the registry to catch the known `write-plan` nested-route metadata drift.
3. Shrink metadata prompts so they select and constrain skills without duplicating full contracts.
4. Centralize global native continuation and artifact-review policy in `advanced-user-input`.
5. Add durable Decision Ledger requirements to specs and plans.
6. Add standard Artifact Review Card guidance.
7. Clean backlog candidate signal and generated-state handling.
8. Add golden-path workflow fixtures.
9. Add worker handoff and PR-ready packet examples.
10. Run targeted live-sync, tracker, and align drift validation.

## Architecture

The architecture has four layers.

### Contract Layer

Add a machine-readable workflow contract under a source-owned path such as `docs/superpowers/workflow-contract.yml`.

The contract should include:

- skill name and canonical invocation name;
- route purpose and owner;
- owning artifact roots;
- native question IDs;
- prompt text;
- top-level options;
- nested Yes-route options;
- nested Revisit-route options;
- terminal state rules;
- final health gate rules;
- required validators before closeout, merge, live sync, or Done;
- expected output artifacts;
- allowed next-skill transitions;
- generated documentation surfaces;
- metadata summary fields.

The registry must treat `advanced-user-input` as the central helper for native input policy. It can be included as a helper entry, but it must not be treated as an implementation route.

### Validation And Generation Layer

Add focused validators and, where useful, generation scripts that consume the contract.

Required checks:

- every active workflow skill appears in the contract;
- every native question ID in workflow `SKILL.md` files appears in the contract;
- nested Yes-route options do not contain terminal options;
- nested Revisit-route options do not contain terminal options;
- final-capable skills are declared once;
- generated or summarized docs match contract values;
- metadata route summaries match contract values;
- duplicated global policy blocks are rejected outside `advanced-user-input`;
- `.superpowers/**` generated state is ignored by canonical audits unless a run-ledger review is explicitly selected.

### Authoring Layer

Improve the human and agent authoring surfaces without weakening proof gates.

Required additions:

- compact `agents/openai.yaml` prompts that say when to select the skill, the hard boundaries, and that `SKILL.md` plus the contract own detailed behavior;
- `## Decision Ledger` in specs and plans;
- standard Artifact Review Card schema for closeout and permission gates;
- active backlog source that separates current candidates from historical plan checkboxes;
- examples and packet templates for common routes and worker handoffs.

### Execution Layer

Downstream execution should remain owned by existing skills:

- `brainstorm-spec` owns this spec and later spec revisions.
- `write-plan` owns the implementation plan.
- `create-issues` owns issue mirror and GitHub issue creation when selected.
- `resolve-issue` or `orchestrate-issues` owns issue implementation.
- `merge-changes` owns merge closeout, branch/worktree cleanup, issue close proof, live sync proof when applicable, and clean repo proof.
- `align-project` owns source/live/tracker drift repair.
- `loop-controller` coordinates repeated candidate selection but does not bypass route owners.

## Data Flow

1. Audit findings enter the repo through this spec.
2. `write-plan` turns this spec into one implementation plan with track-level tasks and Outcome Proof.
3. `create-issues` can split the plan into issue mirrors and GitHub issues when the plan chooses issue-backed execution.
4. The registry becomes the authoritative route data source.
5. Validators consume the registry and compare README, generated workflow docs, skill route sections, metadata summaries, fixtures, and runtime ledgers.
6. Decision Ledger and Artifact Review Card schemas flow into specs, plans, issue mirrors, closeout evidence, and merge packets.
7. `merge-changes` verifies the implemented evidence still satisfies the plan proof before integration.

## Error Handling

- Route contradictions fail validation.
- Missing registry entries fail validation.
- Native question IDs present in skills but absent from the registry fail validation.
- Terminal options inside nested Yes or Revisit routes fail validation.
- Full global-policy paragraph duplication outside `advanced-user-input` fails validation once the central policy lands.
- Metadata prompts that exceed the agreed compact contract or duplicate route tables fail validation.
- Decision Ledger sections missing required columns fail ready-state validation.
- Artifact Review Cards missing path, proof, decision, risk, or next-route fields fail scenario validation.
- Tracked `.superpowers/**` generated state fails validation.
- Live sync drift fails `scripts/sync-live.ps1 -Validate`.

The repair policy is loud failure with a targeted next route. Do not add compatibility wrappers or silent alternate behavior for stale route surfaces.

## Non-Goals

- Do not create a new workflow route for contract normalization.
- Do not replace existing route-owning skills.
- Do not make Loop Controller an implementation shortcut.
- Do not weaken native user approval, merge approval, push permission, final Done, or live-sync proof gates.
- Do not move canonical artifacts into milestone-local folders.
- Do not treat `.chatgpt/**` or `.superpowers/**` as canonical project documentation.
- Do not make GitHub Projects mandatory as part of this repair.

## Risks

- The registry can become another duplicated surface if validators do not make it authoritative.
- Compressing skill text too aggressively could hide route-specific hard gates; each skill must keep skill-specific question IDs, required artifacts, and route boundaries.
- Generated docs can obscure review if scripts rewrite large sections without focused diffs; validators should produce precise mismatch messages.
- The umbrella plan may be large; issue creation should split tracks into independently mergeable vertical slices.
- Backlog cleanup can accidentally hide active work if plan statuses are inferred too loosely; use explicit active sources when possible.
